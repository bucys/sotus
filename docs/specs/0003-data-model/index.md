# 0003. Data model: shared recipes, private collections, signed publication

**Date**: 2026-09-30
**Status**: Accepted

Builds the tables, functions and policies that [0001](../0001-stack-architecture/index.md) (attempt table, quota functions, atomic save) and [0002](../0002-recipe-from-youtube-link/index.md) (YouTube columns, save RPC with attempt ID) asked #3 to design. Where this spec and 0002 once differed (duplicate handling, `extraction_method` values, the save call), this spec is the source and 0002 has been updated to match.

## Summary

Every recipe lives once, in one shared library that every signed in user can read. Each library recipe is the canonical Sotus snapshot (a checked copy taken once) of its source link: nobody edits it in the app, and the person who first imported it is credited as "added by" but gets no special rights over it. Your collection is exactly the recipes you have saved: importing a link saves its recipe for you, whether the import created it or found it already there, and you can unsave any recipe, including one you imported. Saving just points at the shared snapshot. Personal changes come later (#13) as your own layer on top, never touching the shared recipe. A new recipe can only enter the library through one database function that takes the importer and the source link from the database itself and accepts content only when it carries a signature (a keyed hash) that only the Sotus server can make, so nobody can plant a fake recipe on a real link by calling the database directly. Pasting a link that is already in the library never creates a copy: you land on the existing recipe and it is added to your collection.

## Requirements

**User stories**:
- As a signed in cook, I want every recipe anyone added to be readable by me, so the library is shared.
- As a signed in cook, I want every recipe I import or save to land in my collection, and to be able to remove any of them, so I have my own list.
- As a signed in cook, I want a saved recipe to stay exactly as Sotus extracted it, so nobody else can change a recipe in my collection.
- As a signed in cook, I want a link someone already added to open that recipe and put it in my collection, so the library holds no duplicates.
- As a signed in cook, I want every library recipe to have come through Sotus's own extraction, so nobody can plant a fake recipe on a real link.

**Acceptance criteria**:

- **AC-1**: `save_recipe` called with a valid `started` extraction attempt of the caller, a valid payload and a valid signature creates, in one transaction, one `recipes` row, its `recipe_ingredients` and `recipe_steps` in the given order, a `saved_recipes` row for the caller, and finishes the attempt as `recipe` with the tokens passed and `recipe_id` set. It returns `{ out_recipe_id, out_created: true }`. If any part fails, nothing is written and the attempt stays `started`.
- **AC-2**: In the recipe `save_recipe` creates, `added_by` is `auth.uid()`, `source_kind` comes from the attempt's `kind`, and `source_url` is the attempt's `source_url`. The payload has no attribution or source fields, and any it carries are ignored. `source_url_key` and `youtube_video_id` are generated by the database from `source_url` and cannot be written by anyone.
- **AC-3**: `save_recipe` raises and writes nothing when: the signature is missing or does not match (`invalid_signature`); the publish secret is not configured (`publish_not_configured`); the attempt does not exist, belongs to another user, is not `started`, or is a `cook_pick` attempt (`attempt_not_found`); tokens are negative (`invalid_arguments`); or the payload is invalid (`invalid_recipe`). Invalid means: not a JSON object; `ingredients` or `steps` not an array; an ingredient not an object; any string field not a string; a required value blank (no non whitespace character); `extraction_method` not matching the source kind; `source_channel_title` on a web attempt; or a limit broken (title 1 to 120 characters, 2 to 60 ingredients, ingredient name 1 to 120, quantity up to 40, unit up to 20, 1 to 40 steps, step 1 to 1000, `source_title` and `source_channel_title` up to 300, `recipe_page_url` present exactly when the method is `youtube_recipe_page_jsonld`, `http` or `https`, at most 2048 bytes). Blank ingredients or steps fail; they are never dropped.
- **AC-4**: When a recipe with the same `source_url_key` (web) or `youtube_video_id` (YouTube) already exists, `save_recipe` creates no second recipe, even when two calls race. It inserts a `saved_recipes` row for the caller and the existing recipe (`on conflict do nothing`, so an existing save stays one row), finishes the attempt as `recipe` / `already_saved` with `recipe_id` set to the existing recipe, and returns `{ out_recipe_id, out_created: false }`.
- **AC-5**: `open_existing_recipe(kind, url)` returns the ID of the recipe whose key matches the URL, and inserts a `saved_recipes` row for the caller (`on conflict do nothing`), including when the caller is its `added_by` and had unsaved it. It returns null and writes nothing when no recipe matches, when the URL is invalid, or when a `web` lookup gets a YouTube host. It never creates or touches an attempt row.
- **AC-6**: Every signed in user can read every recipe, its ingredients and steps, and every profile's `display_name` and `avatar_url`. An anonymous request is denied on every table, view and RPC.
- **AC-7**: Canonical recipe content is read only for every signed in user, including the one who added it: any direct insert, update or delete on `recipes`, `recipe_ingredients` or `recipe_steps` is denied, as is any direct write to `profiles` or `ai_attempts`. `added_by` is attribution only and affects no permission and no collection membership.
- **AC-8**: `updated_at` changes only when canonical content columns change (a future privileged path such as an admin fix or a re-extraction), set to `clock_timestamp()` by a trigger; `created_at` never changes. Changing `added_by` (account deletion) leaves `updated_at` as it was.
- **AC-9**: `saved_recipes` is the only source of collection membership. A user can save and unsave any recipe, including one they imported (unsaving it leaves the recipe and its `added_by` unchanged); saving twice is not an error and keeps one row. A user reads only their own saves. The `my_collection` view returns exactly the recipes with a save row for the caller, each once, newest first by save time. Every user sees the same canonical content for the same recipe.
- **AC-10**: `reserve_ai_attempt(kind, source_url)` trims the URL, then inserts a `started` attempt owned by the caller and returns its ID only when today's counts (UTC day, database clock) are under 20 for `extract_web` plus `extract_youtube` per user, 30 for `cook_pick` per user and 300 for all kinds app wide (per user and app wide limits both raise `quota_exceeded`; nothing is inserted). Concurrent calls never overshoot a limit. It raises `invalid_source_url` when: a YouTube URL is not the canonical watch URL; a web URL is not `http`/`https`, has user info (`user:pw@`), a port other than 80 or 443, is over 2048 bytes, has a YouTube host, or yields no `web_url_key`; an extraction kind has a null URL; or a `cook_pick` has any URL.
- **AC-11**: `finish_ai_attempt` sets the outcome, reason, tokens and `finished_at` only on the caller's own `started` attempt, at any age. It refuses `started` and `recipe` as outcomes (`invalid_outcome`; a `recipe` outcome is only ever set by `save_recipe`) and a reason over 60 characters or negative tokens (`invalid_arguments`). Users read only their own attempts.
- **AC-12**: A new `auth.users` row gets a `profiles` row with `display_name` from the Google `full_name`, else `name`, else `Sotus cook` (blank values skipped, cut to 100 characters), and `avatar_url` from the Google `avatar_url` only when it is `https` and at most 2048 bytes, else null. The trigger never blocks a sign up.
- **AC-13**: Deleting a user removes their profile and saves. Their attempts stay with `user_id` null and still count toward the app wide daily limit. Recipes they first imported stay in the library with `added_by` null and content, `updated_at` and other users' saves unchanged; #8 shows "Added by a former member".
- **AC-14**: A YouTube recipe stores `source_metadata_fetched_at` (the time `save_recipe` ran, standing for when the Data API values were fetched in the same request); a web recipe stores null.
- **AC-15**: `supabase/tests/rls.sql` proves AC-1 to AC-14, the `web_url_key` examples and the privilege rules (no role outside the owner can call a `private` helper, and every permitted path that writes `recipes` computes the generated columns without a permission error) as two users and as anonymous against `sotus-dev`, and a row count taken after its rollback shows no rows left behind.

## Decision

**Chosen option**: Option 1: Relational model, writes through guarded Postgres functions, dedup keys generated by the database, recipe publication signed by the server.

Recipes, ingredients, steps, saves, profiles and attempts are plain relational tables under RLS. A recipe is a canonical snapshot of its source: users never modify it, and `added_by` is attribution, not edit authority. Every recipe insert and every attempt write goes through a `SECURITY DEFINER` function that takes the importer from `auth.uid()` and the source from the attempt. The duplicate keys are generated columns backed by unique constraints, so the database alone decides identity and races. `save_recipe` also requires an HMAC signature made with a secret only the Sotus server and the database's Vault hold, so only Sotus's own extraction pipeline can publish into the shared library.

**Implementation skills**: `supabase` (`~/.claude/skills/supabase/`) · `supabase-postgres-best-practices` (`~/.claude/skills/supabase-postgres-best-practices/`)

## Feature design

### Data model sketch

Schemas: tables, the `my_collection` view and callable RPCs in `public`. Helpers the API must not expose (trigger functions, URL key functions) live in a `private` schema with no grants to `anon` or `authenticated`. Extensions used: `pgcrypto` (in `extensions`, on by default in Supabase) and Supabase Vault.

**Enums** (`public`):

| Enum | Values |
|---|---|
| `source_kind` | `web`, `youtube` |
| `extraction_method` | `web_jsonld`, `web_model`, `youtube_recipe_page_jsonld`, `youtube_description`, `youtube_transcript` (unused until 0002 slice 2) |
| `ai_attempt_kind` | `extract_web`, `extract_youtube`, `cook_pick` |
| `ai_attempt_outcome` | `started`, `recipe`, `not_a_recipe`, `insufficient`, `ingestion_failed` (#12 adds its own success value by migration) |

**`my_collection`** view (`with (security_invoker = true)`, so RLS of the caller applies): `saved_recipes` inner joined to `recipes`, where `saved_recipes.user_id = auth.uid()`, with `added_at = saved_recipes.created_at`. The primary key `(user_id, recipe_id)` makes each recipe appear once.

**Indexes** (beyond primary keys and the two unique constraints): `recipes (created_at desc, id desc)` for the library; `recipes (added_by)`; `saved_recipes (recipe_id)`; `ai_attempts (user_id, created_at)` and `ai_attempts (created_at)` for quota counts; `ai_attempts (recipe_id) where recipe_id is not null`.

**URL key functions** (`private`, `language sql strict immutable parallel safe`, the one normalization used by generated columns and RPCs alike):
- `private.youtube_video_id(url)`: the 11 character ID when `url` matches `^https://www\.youtube\.com/watch\?v=([A-Za-z0-9_-]{11})$`, else null.
- `private.web_url_key(url)`, **conservative**: a false merge sends people to the wrong recipe, a missed merge only leaves a duplicate, so it changes as little as possible. Null unless the URL parses as `http(s)://host[:port]/…` with no user info. Then: lowercase the scheme and host; drop the port only when it is the scheme's own default (`:80` for `http`, `:443` for `https`), keeping any other port; drop the fragment; drop query parameters whose name, compared without case, is `utm_*`, `fbclid`, `gclid`, `igshid`, `mc_cid` or `mc_eid`, keeping the rest in order and unchanged; drop a `?` left with nothing after it. Everything else is kept as is: `www.`, the scheme, the path and its case, a trailing slash, percent encoding, other parameters.

### Signed publication

The rule the signature enforces: a recipe row can only be created from a payload the Sotus server produced for this user's own attempt.

- **Secret**: `RECIPE_PUBLISH_SECRET`, 32 random bytes as hex. Held in Vercel (server only) and in Supabase Vault as the secret named `recipe_publish_secret`. It is never in a migration, the repo, a log or the browser.
- **Server side** (`src/lib/recipes/sign-payload.ts`, `import "server-only"`): `payload = JSON.stringify(recipe)`; `signature = hex(HMAC_SHA256(secret, attempt_id + ":" + user_id + ":" + payload))` with `node:crypto`. The secret is read and validated where read, throwing when absent (like `src/lib/supabase/env.ts`). The Server Action calls `save_recipe` with the same `payload` string, so the bytes signed are the bytes sent.
- **Database side**: `save_recipe` reads the secret from `vault.decrypted_secrets` (fails closed with `publish_not_configured` when absent), recomputes `encode(extensions.hmac(convert_to(p_attempt_id::text || ':' || auth.uid()::text || ':' || p_payload, 'UTF8'), convert_to(secret, 'UTF8'), 'sha256'), 'hex')`, and raises `invalid_signature` on mismatch, before anything else is read from the payload.
- **Replay**: the signature binds the attempt and the user; the attempt must be `started` and is finished in the same transaction, so a signature works once.
- **Scope of trust**: the secret authorizes only "publish this payload for this user's own open attempt". It cannot read data, act as another user or skip RLS, unlike a service role key. It proves the content came through Sotus's fetch, Gemini and grounding steps, not that the content is correct (0002's content risks stand).
- **Rotation**: generate a new value, set Vault first, then Vercel, then redeploy. Saves in flight during the switch fail as `invalid_signature` → `ingestion_failed` and the user retries.

### Functions

All RPCs are `SECURITY DEFINER`, `VOLATILE`, `set search_path = ''`, fully qualified names, `revoke execute … from public, anon, authenticated`, then `grant execute … to authenticated`. Each raises `not_authenticated` when `auth.uid()` is null. Errors are raised with the listed message as the exception text; `src/lib/ai/attempt-reasons.ts` maps each known text, and any unknown database error becomes `ingestion_failed`. The map, all as outcome `ingestion_failed`: `quota_exceeded` → reason `quota_exceeded`; `invalid_source_url` → `blocked_url`; `invalid_recipe` → `invalid_model_output`; every other known text (`invalid_signature`, `publish_not_configured`, `attempt_not_found`, `invalid_arguments`, `invalid_outcome`, `not_authenticated`, `recipe_not_resolved`) and any unknown text → `save_failed`. `save_failed` is the one reason this spec adds beyond 0002's list and `already_saved`: these errors mean Sotus's own save step failed (a secret mismatch, a bug, a lost attempt), none of 0002's reasons fits, and the user can only retry. The lookup uses a `Map`, not an object, so a message such as `constructor` cannot hit the prototype.

**`reserve_ai_attempt(p_kind ai_attempt_kind, p_source_url text) returns uuid`**: trims the URL; validates it per AC-10 (web validity is "`private.web_url_key` is not null", plus the host, port, user info and byte checks); takes `pg_advisory_xact_lock(hashtext('reserve_ai_attempt'))` **before** counting; counts today's rows (`created_at >= date_trunc('day', now() at time zone 'utc') at time zone 'utc'`), app wide including rows with a null `user_id`; inserts the `started` row. Limits are constants in the function body. Raises `invalid_source_url`, `quota_exceeded`. YouTube hosts for the web check: `youtube.com`, `www.youtube.com`, `m.youtube.com`, `youtu.be` (same list as 0002).

**`finish_ai_attempt(p_attempt_id uuid, p_outcome ai_attempt_outcome, p_reason text, p_input_tokens int, p_output_tokens int) returns void`**: updates the caller's `started` row, sets `finished_at = clock_timestamp()`. Raises `attempt_not_found`, `invalid_outcome`, `invalid_arguments`.

**`save_recipe(p_attempt_id uuid, p_payload text, p_signature text, p_input_tokens int, p_output_tokens int) returns table (out_recipe_id uuid, out_created boolean)`** (supabase-js returns an array; the caller takes `[0]`):
1. Verify the signature (see *Signed publication*). Check tokens ≥ 0 or `invalid_arguments`.
2. Lock the attempt: `select … for update` where `id = p_attempt_id and user_id = auth.uid() and outcome = 'started' and kind in ('extract_web', 'extract_youtube')`. None → `attempt_not_found`.
3. Parse `p_payload::jsonb` (a parse error → `invalid_recipe`). Read only `title`, `extraction_method`, `recipe_page_url`, `source_title`, `source_channel_title`, `ingredients[{ name, quantity, unit }]`, `steps[string]`. Check every type with `jsonb_typeof`; `btrim` strings; turn blank optional values into null; apply AC-3. Any failure → `invalid_recipe`.
4. `insert into public.recipes (added_by, source_kind, source_url, title, extraction_method, recipe_page_url, source_title, source_channel_title, source_metadata_fetched_at) values (auth.uid(), <kind mapped>, <attempt.source_url>, …, <clock_timestamp() when youtube>) on conflict do nothing returning id`.
5. Inserted: insert ingredients and steps with `position` from `with ordinality`; insert `(auth.uid(), id)` into `saved_recipes`; finish the attempt (`recipe`, reason null, tokens, `recipe_id`, `finished_at`); return `(id, true)`.
6. Not inserted (a key already exists, including a concurrent winner; under read committed the conflicting insert waits for it, and the next statement sees its row): select the existing recipe by the attempt URL's key; insert `(auth.uid(), id)` into `saved_recipes` `on conflict do nothing`; finish the attempt (`recipe`, `already_saved`, tokens, `recipe_id`); return `(id, false)`.

**`open_existing_recipe(p_kind source_kind, p_source_url text) returns uuid`**: trims, computes the key with the same private function (null for an invalid URL or a YouTube host on `web`), looks up the recipe; on a match inserts the caller's save row (`on conflict do nothing`) and returns its ID; else null. Used before `reserve_ai_attempt`, so a known link costs no quota. Needs no signature: it only links an existing recipe to the caller.

**Triggers** (functions in `private`, `SECURITY DEFINER` only where needed, `set search_path = ''`):
- `private.set_updated_at()` on `recipes` `BEFORE UPDATE OF` the content columns (see the `updated_at` row).
- `private.handle_new_user()` `after insert on auth.users` (`SECURITY DEFINER`): `display_name = left(coalesce(nullif(btrim(meta->>'full_name'), ''), nullif(btrim(meta->>'name'), ''), 'Sotus cook'), 100)`; `avatar_url` = the metadata value only when it starts with `https://` and is at most 2048 bytes, else null. The migration backfills profiles for existing `auth.users` rows (`on conflict do nothing`).

### Row level security and grants

RLS on every table. Policies are `to authenticated` and use `(select auth.uid())`.

| Object | select | insert | update | delete |
|---|---|---|---|---|
| `profiles` | everyone (`true`) | none (trigger) | none | none |
| `recipes` | everyone | none (`save_recipe`) | none (canonical, read only) | none |
| `recipe_ingredients`, `recipe_steps` | everyone | none | none | none |
| `saved_recipes` | `user_id = auth.uid()` | `with check (user_id = auth.uid())` | none | `user_id = auth.uid()` |
| `ai_attempts` | `user_id = auth.uid()` | none | none | none |
| `my_collection` (view) | through the underlying policies (`security_invoker`) | n/a | n/a | n/a |

Privileges, written explicitly because Supabase grants `anon` and `authenticated` everything on new objects in `public` by default:
- `revoke all on` every table and the view `from anon, authenticated`; then grant to `authenticated`: `select` on all tables and the view, and `insert, delete` on `saved_recipes`. No `update` grant on any table.
- `revoke all on schema private from public, anon, authenticated`; `revoke execute on all functions in schema private from public, anon, authenticated`. `private` is not in the Data API's exposed schemas, so its objects have no HTTP route either.
- Function grants as in *Functions*.
- **Closed by default** for every later migration (run as `postgres`, the role that creates objects here):
  - `alter default privileges for role postgres in schema public, private revoke all on tables from anon, authenticated;`
  - `alter default privileges for role postgres in schema public, private revoke all on sequences from anon, authenticated;`
  - `alter default privileges for role postgres revoke execute on functions from public;` (global, every schema)
  - `alter default privileges for role postgres in schema public, private revoke execute on functions from anon, authenticated;` (removes Supabase's own per schema grants)
  - Why the function line is global: Postgres adds per schema default privileges on top of the global ones, and the global default gives `EXECUTE` on every new function to `PUBLIC`, which includes `anon` and `authenticated`. A per schema `revoke … from public` cannot remove a global grant, so it changes nothing. Checked on `sotus-dev` during the build: with only the per schema form, `authenticated` could execute a newly created function; with the global form, it could not.
  - Each feature then grants exactly what it needs, in its own migration. Because the function revoke is global, it also covers functions `postgres` creates outside `public` and `private`, including those a later `create extension` run as `postgres` adds. If such an extension's functions must be callable by the app, that feature's migration grants `execute` on them explicitly.

**Generated column helpers and privileges.** `private.web_url_key` and `private.youtube_video_id` are owned by `postgres`, the same owner as `recipes`, and nobody else holds `EXECUTE` on them. Postgres checks `EXECUTE` on a function in a generated column expression against the role doing the write when it computes the column. That holds safely here because every permitted write path to `recipes` runs as `postgres`:
- `save_recipe` inserts as its definer (`postgres`).
- Account deletion sets `added_by` to null through the foreign key action, which Postgres runs as the owner of `recipes` (`postgres`), whichever role deleted the user.
- `authenticated` and `anon` have no insert or update grant on `recipes`, so they never reach the expression.

So the minimum is no helper grant at all. A future feature that lets `authenticated` write `recipes` directly would need `grant execute` on both helpers to `authenticated` (still unreachable over HTTP, since `private` is not exposed). The better path is to keep writes in a `SECURITY DEFINER` function. The test script proves both permitted paths and the denial (see *Critical test scenarios*).

### Read paths (for #8, #9, #11)

- **Library** (#9): `recipes` ordered `created_at desc, id desc`, with `profiles(display_name, avatar_url)` embedded through `added_by`, 20 per page, keyset filter `or=(created_at.lt.<ts>,and(created_at.eq.<ts>,id.lt.<id>))`. The cursor carries the raw timestamp string from the row, never a JS `Date` (which drops microseconds).
- **Recipe page** (#8): one recipe with ingredients and steps ordered by `position`, the `added_by` profile, and whether the caller has a save row.
- **My collection** (#11): `my_collection` ordered `added_at desc, id desc`, same keyset style.
- **Save** (#11): `insert` into `saved_recipes` with `ignoreDuplicates: true` (`on conflict do nothing`; a merging upsert would need an update grant). **Unsave**: `delete` by `recipe_id`.

### State transitions

`ai_attempts.outcome`: `started` → `recipe` (only `save_recipe`) | `not_a_recipe` | `insufficient` | `ingestion_failed` (`finish_ai_attempt`). Terminal after that. A `started` attempt may be finished at any age. Showing an old `started` row as `interrupted` is #10's read rule (0001), not a column or view here.

### Key invariants

- One recipe per `source_url_key` and one per `youtube_video_id`, enforced by unique constraints on generated columns; the loser of a race resolves to the winner inside `save_recipe`.
- A recipe row exists only if `save_recipe` accepted a server signature over its exact payload for the caller's own open attempt.
- A library recipe is a canonical snapshot of its source: no signed in user can change its content, ingredients or steps, including the one who added it. The source URL is provenance and dedup identity; the snapshot does not follow later changes to the source.
- `added_by` is attribution only; no policy, function or view reads it for permissions or collection membership.
- `added_by` and the source identity come only from `auth.uid()` and the caller's own attempt, never from the payload.
- A recipe has at least 2 ingredients and 1 step, because only `save_recipe` inserts and it checks the counts in the same transaction.
- `outcome = 'recipe'` only through `save_recipe`, which sets `recipe_id` in the same transaction.
- Attempts are never deleted, so the app wide count holds after account deletion.
- A user's collection = their `saved_recipes` rows, nothing else. Every successful import (new or duplicate) leaves the importer with a save row for its recipe.
- Deleting a user removes their save rows; for recipes they first imported it changes only `added_by` (to null); the recipe, its `updated_at` and other users' saves stay.
- No recipe is deleted in this release.
- No role other than `postgres` can execute a `private` helper, and every object a later migration creates starts with no grants for `anon` or `authenticated`.

### Security model

- The app uses the publishable key plus the user's session; no service role key (AGENTS.md). The one extra secret, `RECIPE_PUBLISH_SECRET`, can only authorize a publication (see *Signed publication*).
- Auth configuration assumed by every policy: Google is the only enabled provider, email sign up and anonymous sign ins are off (#5 sets this). Otherwise sign up metadata would be attacker controlled and anonymous users would pass `to authenticated` policies.
- Anonymous requests are denied on every object.
- Everyone signed in reads all recipes and all profiles (name and avatar only; no email in `profiles`).
- Saves and attempts are private to their user.
- Writes to recipes, attempts and profiles happen only in `SECURITY DEFINER` functions with `search_path = ''`. Helpers sit in `private`, which the Data API does not expose.
- A user calling RPCs directly can: spend their own quota (`reserve_ai_attempt`), close their own attempts (`finish_ai_attempt`), and save existing recipes (`open_existing_recipe`). None of these touches shared content.
- Pasted URLs are stored and readable by every signed in user. User info is rejected, but other query parameters are kept, so a private token in a pasted URL becomes visible to other users. Accepted; #6's form hint may say so.
- YouTube API data (`source_title`, `source_channel_title`) is stored with `source_metadata_fetched_at`. YouTube's developer policies limit how long such data may be kept without a refresh; acceptable for the non commercial demo, a launch gate before any public use (Follow-up).
- Personal data: Google display name and avatar URL. No compliance scope beyond 0001.

### Configuration required

- `RECIPE_PUBLISH_SECRET`: server only; 32 random bytes as hex (`openssl rand -hex 32`). Add to Vercel (all three environments), `.env.local`, and `.env.example` without a value.
- Vault secret: run once in the Supabase SQL editor on `sotus-dev`: `select vault.create_secret('<same value>', 'recipe_publish_secret');`. Never in a migration.
- Supabase Auth (#5): Google only; email provider and anonymous sign ins off.
- To run `supabase/tests/rls.sql`: the `sotus-dev` connection string in your shell (for example `SUPABASE_DB_URL`, never committed) and `psql` (`brew install libpq`), or paste it into the SQL editor. Run it when today's app wide attempt count is under 270, since the quota scenario adds 21 attempts inside the rolled back transaction.

### Critical test scenarios

`supabase/tests/rls.sql`: one transaction ending in `rollback`. As `postgres` it inserts users A and B into `auth.users` (firing the profile trigger) and signs payloads with the Vault secret via `extensions.hmac`; it switches identity with `set local role authenticated` plus `set local request.jwt.claims`, and `reset role` before touching `auth.users` again. Every expected failure runs in its own `begin … exception when … end` block that raises if no error occurred. A separate statement after the rollback counts rows to prove nothing remained.

- Happy path: A reserves `extract_web`, signs and calls `save_recipe`; one recipe with `added_by = A`, ingredients and steps in order, one `saved_recipes` row for A, attempt `recipe` with `recipe_id`, verifies **AC-1**, **AC-2**
- Signature: a valid payload with a wrong signature, a signature made for B, and a signature over a different payload all raise `invalid_signature` and write nothing; with the Vault secret renamed inside the transaction, `publish_not_configured`, verifies **AC-3**
- Trust: the payload carries `added_by = B` and `source_url = other`; the row still has A and the attempt URL, verifies **AC-2**
- Invalid: B with A's attempt, a replayed finished attempt, a `cook_pick` attempt → `attempt_not_found`; 1 ingredient, a blank step, `ingredients` as an object, a `web_*` method on a YouTube attempt, `source_channel_title` on web, `recipe_page_url` of `javascript:x` → `invalid_recipe`; negative tokens → `invalid_arguments`, verifies **AC-3**
- Duplicate: B saves `https://example.com/pasta?utm_source=x` after A saved `https://example.com/pasta`; `out_created = false`, one recipe, B has a save row, B's attempt `recipe` / `already_saved`; A unsaves, then imports the same link again through `save_recipe` → `out_created = false` and A has one save row again; `https://www.example.com/pasta` creates a separate recipe, verifies **AC-4**. The true concurrent race is proved in `/check verify` with two sessions.
- Open existing: B calls `open_existing_recipe` on A's link → A's ID, B saved, no new attempt; A calls it while still saved → still one save row; A unsaves, calls it again → A's save row is back; `web` with a YouTube URL → null, verifies **AC-5**, **AC-9**

- Canonical read only: A (who added the recipe) and B are both denied on `update recipes set title`, on any update, insert or delete of `recipe_ingredients` and `recipe_steps`, and on insert or delete of `recipes`; direct insert into `profiles` and `ai_attempts` is denied, verifies **AC-7**

- Collection: A unsaves the recipe A imported → gone from A's `my_collection`, recipe and `added_by = A` unchanged; A saves it again directly → back; B saving twice with `on conflict do nothing` keeps one row; `my_collection` for B lists exactly B's saved recipes (the one B imported and A's) once each in save time order, with the same content A sees; a recipe with `added_by = B` that B has unsaved is absent from B's view, verifies **AC-9**

## Consequences

**Positive**:
- Only Sotus's own pipeline can put a recipe into the shared library, so first writer wins can no longer be abused by a direct database call.
- Identity, attribution, duplicates and quota are enforced in the database, so no feature can get them wrong in app code.
- Races on the same link settle inside one function: the unique constraint picks the winner and the loser still ends on the recipe.
- A pasted duplicate costs no quota and still lands in your collection.
- App wide quota survives account deletion.
- Child tables make ingredient search (#14) and later shopping lists plain SQL; later extras are added tables or nullable columns.

**Negative / tradeoffs**:
- One more secret, held in two places (Vercel and Vault), set by hand and rotated together; a mismatch stops every new recipe until fixed.
- More SQL to get right: four `SECURITY DEFINER` functions, HMAC verification, a URL normalizer in SQL, explicit revokes and default privileges. The RLS script is part of the build because a mistake here is a security bug.
- Conservative URL keys leave more duplicates: `www.` versus no `www.`, `http` versus `https` and a trailing slash all create separate recipes.
- **Nobody can fix a canonical recipe in the app.** A poor but honest extraction (a missed step, a wrong amount) is the library's only copy of that link until an admin path or re-extraction exists; before #13, users can't even patch their own view. First writer wins now means "first extraction wins", which makes the admin path more important.
- The snapshot goes stale when the source changes (a creator fixes their page); there is no refresh.
- `added_by` credits whoever pasted first, not the recipe's author; #8 must word it as "Added by", never "By".
- The earlier product rule "only the person who added a recipe can edit it" (scope boundaries, #13) no longer holds; the scope needs a matching update.
- Pasted query parameters, including any private tokens, are visible to all signed in users.
- The race test is manual in `/check verify`; the script cannot run two transactions.
- The limits (20/30/300) live in function code; changing them is a migration.

**Neutral**:
- #6 and #7 call `open_existing_recipe` before reserving and `save_recipe` with a signed payload, and treat `out_created = false` as "already in the library".
- #13 contract: personal changes live in their own user owned table(s) that reference `recipes(id)` (an overlay or a personal copy, #13 decides), never in `recipes` itself. A copy stored as a `recipes` row would collide with the unique source keys and enter the shared library, so it is ruled out. `my_collection` then gains the personal version. Nothing in this schema has to change for that.
- #12 adds its success outcome to `ai_attempt_outcome` by migration.
- New patterns: generated columns as keys, a `private` schema, closed by default privileges (global for functions), a Vault secret checked in SQL.
